# gorkX 产品开发计划

> **状态：** v0.5.0 Beta 之后的唯一增量路线。  
> **目的：** 做一个以 Grok Build 为内核、比终端更易用、能完成办公与项目工作的桌面 Agent。

## 1. 产品方向

| 方向 | 用户应获得的体验 | gorkX 的处理原则 |
|---|---|---|
| **独立内核** | 用户只安装 gorkX，即可安全登录、运行任务、保存会话与管理模型。 | App 自管 Grok Build、App-owned `GROK_HOME` 与 ACP；不扫描用户 CLI 或共享不透明配置。 |
| **连续工作** | 多个任务能持续推进，用户切换任务后仍看得见运行状态和待决定事项。 | 所有运行状态、进度和通知必须来自真实 ACP 任务。 |
| **成果交付** | 文件、变更、报告、摘要与下一步集中呈现，可检查、可打开、可安全修改。 | 只呈现经内核明确返回并经过本地验证的成果。 |
| **受控协作** | 用户可按需连接工作平台，让任务完成真实外部工作。 | 每个连接器都必须先授权、可断开、可审计，高风险动作逐次确认。 |

## 2. 不可违背的架构规则

1. **Grok Build 仍是唯一 Agent 执行内核。** gorkX 不在 App 层重写 Planner、Worker 或模型循环。
2. **App 层只负责任务生命周期与可视化。** 多会话进程管理、队列、成果索引、审批和本地提醒可以由 gorkX 管；模型决策、工具调用与计划质量仍归内核。
3. **本地优先且隔离。** 运行内核只使用 App-owned `HOME` 与 `GROK_HOME`；不默默读取用户 `~/.grok`、Shell 配置或浏览器登录状态。
4. **连接器先授权再显示可用。** 普通用户走官方 OAuth/系统授权；Token、命令、配置文件只作为高级回退。没有完整链路就显示“未连接 / Soon”。
5. **高风险动作必须可见、可拒绝。** 发送消息、改日程、写远端系统、执行 Shell、外发文件，均显示目标、影响范围和确认按钮；后台任务遇到审批必须暂停，不得自行执行。
6. **结果是产品单位。** 任务完成要清楚给出可打开的文件、链接、变更、摘要与下一步，不能只留下聊天文字或猜测项目目录中的文件。
7. **无假能力。** 每项 UI 必须有真实验收、可复跑证据和失败态；不以 slash 文本、Mock、或静态卡片冒充已实现。

## 3. 能力地图

```text
用户目标
  └─ 快捷入口 / 自然语言描述                         ← gorkX
       └─ Grok Build ACP 会话与工具执行              ← gorkX 内核边界
            ├─ 同时运行的任务、状态、追加引导
            ├─ 计划、权限、外部动作的待审批收件箱
            ├─ 产物、资料、变更的成果工作区
            └─ OAuth 连接器与定时触发
```

## 4. 体验与视觉系统

### 4.1 设计目标

gorkX 应是一个安静、可信、专注的桌面指挥台：用户打开后首先知道正在做什么、下一步能做什么、哪些事项正在等待自己决定。界面不应像设置后台，也不应把所有工具同时摊开。

| 原则 | 设计要求 |
|---|---|
| **任务优先** | 任何时刻，当前任务、运行状态、输入与下一步动作处于视觉中心。 |
| **按需展开** | Review、Terminal、详情、设置等只在需要时出现；空状态不长期占据主舞台。 |
| **深度而非堆叠** | 用背景层级、文字层级、留白、状态色和轻量动效建立空间感，不依赖大量边框和灰色卡片。 |
| **中文优先** | 中文文案短、明确、可操作；英文为同等完整的辅助语言。 |
| **状态可感知** | 运行、等待、需确认、成功、失败、离线等状态均有文字、颜色与图标，不只依赖颜色。 |
| **无障碍可用** | 键盘可到达、焦点明显、状态可读、对比度达标；动效可减弱。 |

### 4.2 视觉基线

1. **深色作为完整主主题，浅色同等维护。** 深色使用接近黑蓝的分层背景，保留 gorkX 的 X 标识与少量冷色高光；不使用大面积纯黑或刺眼霓虹。
2. **建立设计令牌。** 所有颜色、字号、行高、圆角、间距、阴影、边框、图标尺寸和状态色必须来自统一 token，禁止组件自行写一套视觉规则。
3. **减少无效容器。** 卡片只表达可点击对象、可分组信息或明确状态；普通文字区不再套卡片。
4. **输入框是行动中心。** 新任务页与会话页均让输入、附件、模型、权限和发送动作清晰而克制；高级能力收进菜单或上下文面板。
5. **内容结果优先。** 回复中的表格、图、选择项、文件、步骤和计划有统一排版规则，避免“聊天文本 + 随机卡片”混杂。

### 4.3 工作区布局

```text
┌───────────────┬───────────────────────────────────────┐
│ 导航与任务     │ 当前任务主舞台                         │
│               │ 标题 · 项目 · 模型 · 运行状态          │
│ 新建任务       │                                       │
│ 项目与任务     │ 对话 / 计划 / 成果 / 审阅（按需切换） │
│ 运行中心       │                                       │
│ 决策收件箱     │ 输入与快捷入口                         │
│ 账户与设置     │                                       │
└───────────────┴───────────────────────────────────────┘
          右侧详情与底部终端：仅在用户打开或任务需要时显示
```

| 页面 | 必须解决的问题 |
|---|---|
| 首页 | 用户无需先理解项目、模型或命令，也能从“我要完成什么”开始。 |
| 会话页 | 对话、任务进度、工具活动、审批与成果不互相抢占空间。 |
| 运行中心 | 多任务状态一眼可见，点击后回到正确任务。 |
| 成果工作区 | 成果、资料、文件预览和变更有清晰归属，不散落在聊天记录中。 |
| 设置 | 以用户目标分组，可搜索；未连接或不可用能力说清原因和下一步。 |

## 5. 完整能力范围

| 领域 | 用户结果 | 约束 |
|---|---|---|
| 项目与任务 | 选择一个项目或无项目任务，创建、搜索、归档、恢复、置顶和删除任务。 | 不扫描用户磁盘；项目范围始终可见。 |
| 对话与引导 | 流式回复、附件、快捷任务、计划、选择项、旁问、继续指令和停止。 | 命令保留给熟练用户，但不是普通路径。 |
| 多任务运行 | 多个独立任务可被管理、切换、暂停、取消与恢复。 | 仅展示内核真实状态；不伪造后台完成。 |
| 审批与权限 | 文件信任、工具权限、计划审阅、外部动作统一进入可追溯 Decisions。 | 确认必须回到原始任务；断连任务不可被误操作。 |
| 成果与审阅 | 文件、链接、摘要、计划、Diff、工具记录、终端和导出。 | 成果须由 ACP 明确返回并通过本地安全校验。 |
| 记忆与上下文 | 用户、项目和任务记忆可查看、搜索、整理、删除。 | 用户能看见来源和影响范围；不隐藏长期注入。 |
| 模型与提供商 | Grok、API/兼容提供商、本地模型的配置、测试、选择与真实状态。 | 网页订阅不等同 API；不能显示虚假额度。 |
| 连接器 | GitHub、日历、消息、文档与文件服务的连接和受控操作。 | 官方授权优先；权限最小化；可断开、可审计。 |
| 自动化 | 用户安排可回看的周期任务，获得结果或待审批提醒。 | 后台不得静默外发、改日程、推代码或无限重试。 |
| 环境能力 | 浏览器研究、截图附件、工作树、沙箱、扩展、Hooks、诊断。 | 仅接入已验证内核/系统能力；高风险功能默认关闭。 |
| 发布与支持 | 安装、更新、诊断、错误恢复、数据迁移、签名与多平台。 | 不把 Beta 当正式稳定版；每个平台独立验收。 |

## 6. 阶段路线与验收

### 阶段 A：体验基础与视觉重构

**目标：** 让首页、会话页、侧栏、输入框、任务状态和按需面板成为统一体验，而不是在现有页面上继续堆功能。

| 交付 | 完成标准 |
|---|---|
| 设计 token 与组件基线 | 深浅主题、排版、按钮、状态、卡片、菜单、空状态和焦点环均由统一 token 驱动。 |
| 布局重构 | 空 Review/Terminal 不默认占屏；窗口尺寸变化时主任务始终优先。 |
| 首页重构 | 目标输入、快捷入口、项目选择和最近任务清晰，首次使用有明确引导。 |
| 会话视觉重构 | 消息、工具、计划、决定、成果的层级一致；长任务仍可快速定位当前进度。 |
| 视觉验收 | 使用真实任务、空状态、错误状态和窄窗口逐屏检查；键盘焦点与文字对比度通过。 |

### 阶段 B：可信的后台多任务

**用户结果：** 可以新建第二个任务，切走后第一个任务继续运行；用户随时知道每个任务在做什么、是否需要自己决定。

| 交付 | 说明 | 验收 |
|---|---|---|
| 任务运行中心 | 侧栏显示运行/等待审批/已完成/失败四种真实状态及当前工具/计划步骤 | 两个真实 ACP 会话同时运行；切换任务不丢失流、权限或回复。 |
| 统一 Decisions 收件箱 | 跨任务聚合权限、计划审阅、结构化问题；点击只回复原任务 | 在任务 A、B 各触发一个真实请求；确认不会误发给另一任务。 |
| 运行中追加引导 | 任务运行中显示“补充说明”按钮；ACP 支持时走对应旁问/追加路由，否则明确排队为下一轮 | 已验证的内核路由才出现按钮；取消、断连、重开行为可回归。 |
| 卡顿处理 | 仅基于真实流/工具心跳显示“仍在工作 / 继续等待 / 取消” | 人为断开或超时的测试任务能准确进入可恢复错误态；不误报正常长工具调用。 |

**不做：** 不宣传“8/32 并发”这类固定数字，除非在目标机器和内核版本上压测通过。

### 阶段 C：成果与资料工作区

**用户结果：** 一次任务做出的报告、表格、图片、代码变更和资料都集中可看、可打开、可安全编辑。

| 交付 | 说明 | 验收 |
|---|---|---|
| Deliverables 面板 | 仅汇总 ACP 明确返回且本地验证过的成果，按文件/链接/变更分类 | 真实任务返回 Markdown、PDF、图片与代码文件；外部路径、符号链接、猜测出的文件均不出现。 |
| 富预览 | Markdown、图片、PDF、文本/代码优先；Office/视频分阶段接入原生或可靠预览器 | 每种已宣称类型有真实样本、打开/关闭/错误文件测试。 |
| 安全编辑 | 文本与 Markdown 的保存、冲突提示、撤销/重载；二进制只预览不伪装可编辑 | 两窗口修改同一文件时显示冲突；保存限定在选定项目。 |
| 一键交付 | 复制摘要、在 Finder 打开、导出任务记录；仅在真实成果存在时出现 | 不扫描整个项目目录；导出不泄露密钥、隐藏系统路径。 |

### 阶段 D：办公连接器与可控外部动作

**用户结果：** 连接 GitHub、Google/微软日历、Slack/飞书、Notion 等后，Agent 可以完成被授权的实际工作；未连接时不会假装能访问。

| 顺序 | 连接器 | 最小真实闭环 |
|---|---|---|
| 1 | GitHub | 官方浏览器授权 → 读取当前仓库 PR/Checks → 用户确认后创建 PR 或评论。 |
| 2 | 日历 | OAuth → 读取指定日程 → 提议变更 → 用户确认 → 写入 → 回执可见。 |
| 3 | Slack / 飞书 | OAuth/官方应用授权 → 读取选定频道 → 草拟回复 → 用户确认 → 发送并显示回执。 |
| 4 | Notion / Drive | OAuth → 选择页面/文件 → 读取、生成草稿或创建副本 → 用户确认写入。 |

**统一安全合同：** 每个连接器都要有“连接、权限范围、断开、重新认证、失败说明、审计记录”；不使用网页 Cookie、个人浏览器会话或剪贴板 Token 作为静默授权。

### 阶段 E：自动化与异步交付

**用户结果：** 用户可以安排“每日简报”“每周项目状态”等任务；运行过程和任何待确认动作都回到 App，绝不在后台静默外发。

| 交付 | 验收 |
|---|---|
| 自然语言创建计划任务 | 用户可查看频率、时区、数据来源、模型、权限策略与下次运行时间。 |
| 本地计划执行器 | App 关闭后使用受控 macOS Worker；每次运行都有独立任务记录、日志和成果。 |
| 审批暂停与通知 | 后台任务遇到发送/修改操作时进入 Decisions；重开 App 后仍可处理。 |
| 失败与重试 | 显示失败原因和安全的“重新运行”；不隐藏错误、不无限自动重试。 |

### 阶段 F：多模型的真实可用性

**用户结果：** 用户能连接并测试多家 API/兼容提供商，在任务级切换；只显示真实可用的模型和真实返回的用量。

1. 完成至少两个真实 Provider 的“配置 → 模型目录 → 连接测试 → 新任务真实回复 → 记录”闭环。
2. 给每个模型保存非敏感的最后验证时间、失败原因和适用能力（工具调用、图像等）。
3. 保留 Grok OAuth 与 App 自管内核；ChatGPT Plus / Claude Pro 网页订阅不冒充 API 授权。
4. 在每个任务详情中清楚显示实际使用的 Provider/Model，而非只显示默认值。

### 阶段 G：发布可信度与覆盖

| 交付 | 完成标准 |
|---|---|
| macOS 签名与公证 | 从下载到首次启动无需终端绕过；更新、回滚与崩溃诊断有明确流程。 |
| 支持 Apple Silicon 与 Intel | 两种架构分别安装、登录、跑真实项目并通过包内内核验证。 |
| Windows 试验版 | 先通过隔离数据目录、密钥存储、内核启动、真实任务与安装卸载验收。 |
| Linux 评估 | 仅在密钥存储、沙箱、桌面集成与支持成本可控后进入 Beta。 |

## 7. 阶段门禁与优先级纪律

1. **先完成阶段 A，再做阶段 B。** 视觉结构不清晰时继续叠加功能，只会进一步增加认知负担。
2. **阶段 B 通过后，才做阶段 C。** 没有真实后台任务状态，成果面板和自动化会成为假工作流。
3. **连接器按一个样板做完整，再扩展。** 首个连接器必须有连接、断开、读、确认写、审计和失败恢复。
4. **自动化必须晚于审批收件箱。** 没有可靠暂停/恢复，不能允许后台外部动作。
5. **多模型只以真实推理验收为准。** 配置可保存或 `session/set_model` 成功，都不等于模型可用。
6. **每个阶段结束才评估发版。** 默认只推源码；没有用户明确批准，不打 tag、不发 Release、不做 DMG。

## 8. 后续执行顺序（本轮不执行）

计划确认后，按以下顺序启动：

1. 为阶段 A 建立设计 token、页面清单、真实场景截图和视觉验收标准。
2. 完成主工作区结构与首页/会话页/侧栏的视觉重构，再进行交互走查。
3. 审计 ACP Session Manager，确认能否安全保有多个 live 会话和独立事件流。
4. 写两个会话的隔离回归：并行流、切换、权限、计划、取消、断连重连。
5. 做运行中心与 Decisions 收件箱，只消费已存在的真实事件。
6. 以一个真实 Git 项目和一个文档项目做人工验收。
7. 后续阶段每一项均先补齐安全合同、验收记录和失败态，再进入下一项。

## 9. 真链路交付要求（禁止取巧，不是放弃功能）

| 目标 | 真实做法 | 首个可发布验收 | 禁止的取巧方式 |
|---|---|---|---|
| **持续维护内核能力** | 继续以 Grok Build 为唯一执行内核；需要桌面控制面时，通过稳定 ACP/CLI 接口或维护的内核补丁提供。 | 每次内核升级均完成协议探测、回归与包内验证；有用能力在桌面中有真实入口。 | 在 App 层另写一个不可验证的 Planner/Worker 循环，导致与内核行为分叉。 |
| **多模型** | 使用各提供商公开 API、用户自己的 API Key、官方 OAuth 或合法兼容网关；密钥进入 Keychain，模型须真实连接测试。 | 至少两个 Provider 完成“授权/配置 → 拉取或确认模型 → 测试推理 → 任务真实回复 → 断开”闭环。 | 读取网页 Cookie、把网页订阅显示为 API 已连接、只验证保存配置或 `set_model`。 |
| **消息、日历、邮件、文档连接器** | 一个服务一个官方授权流程：连接、权限范围说明、读取、拟稿/预览、用户确认写入、回执、断开、审计。 | 首个连接器完成真实读写闭环；随后按同一安全合同接入其它服务。 | 粘贴不明 Token、复用浏览器会话、未授权即显示可读写。 |
| **浏览器与电脑能力** | 浏览器使用隔离配置与用户明确的来源范围；电脑能力采用 macOS 系统授权、可见操作、紧急停止与逐步确认。 | 浏览器完成指定来源的真实研究任务；电脑能力完成用户触发的捕获/授权/停止验收。 | 静默使用用户浏览器 Cookie、后台截图、无提示控制鼠标键盘。 |
| **自动化任务** | 本地计划执行器按任务保存模型、范围、时区、权限策略和成果；外部写操作进入 Decisions 并等待用户。 | 真实周期任务生成成果；遇到外部写操作会暂停、通知、重开后可继续处理。 | 静默发消息、改日程、推代码、无限重试或访问未选定目录。 |
| **功能完成标准** | 每一项都有单元/协议门禁、真实项目人工验收、失败态、数据边界检查和可回看证据。 | 在功能矩阵中可标为 Real，并附上对应证据路径/步骤。 | 只靠界面截图、Mock、静态文案或 slash 命令存在即宣称完成。 |

### 9.1 实施顺序

1. **先把内核桌面化链路做稳：** ACP 能力审计、内核补丁、回归与包内验证。
2. **再完成多模型真实推理：** 从已有 Provider 配置与连接测试开始，补齐第二个真实 Provider 和断开流程。
3. **以 GitHub 为连接器样板：** 完整做出授权、读取、确认写、回执、断开和审计，再扩展日历、消息、文档服务。
4. **完成浏览器与电脑的可见、可中断控制：** 先浏览器研究，后系统授权的电脑能力。
5. **最后开放自动化：** 只有 Decisions、恢复、日志和紧急停止经真实验收后，才允许周期运行。

### 9.2 每项真实验收的共同门槛

- 用户不需要手改配置文件、执行终端命令或提供浏览器 Cookie。
- 权限范围、将要发生的外部动作与结果回执在界面中可见。
- 密钥、会话凭据、附件私有路径和模型响应正文不写入日志、导出或普通数据库字段。
- 断网、授权过期、用户拒绝、应用重开、任务取消和目标资源消失都有明确失败态。
- 真实验收不使用用户生产数据做破坏性测试；需要外部写入时使用可恢复的测试对象并清理。
