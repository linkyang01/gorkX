# gorkX 融合优势开发计划

> **状态：** v0.5.0 Beta 之后的唯一增量路线。  
> **参考：** gorkX 当前真实能力、Grok App v0.1.8、OpenWorker。  
> **目的：** 做一个以 Grok Build 为内核、比终端更易用、能完成办公与项目工作的桌面 Agent；不是把三个项目拼在一起。

## 1. 产品结论

| 来源 | 必须保留 / 吸收的优势 | gorkX 的处理原则 |
|---|---|---|
| **gorkX** | App 自管 Grok Build、App-owned `GROK_HOME`、ACP、计划/权限/Review/Worktree/记忆、中文结果导向入口 | 这是安全与内核边界，不能为了兼容而退回扫描用户 CLI 或共享不透明配置。 |
| **Grok App** | 后台多会话、运行中追加指令、资源工作区、会话搜索/置顶、卡顿恢复、桌面完成度、跨平台发布 | 优先学习“一个人连续做很多事时仍不丢任务”的体验；所有后台状态必须来自真实 ACP 任务。 |
| **OpenWorker** | 成果交付、官方 OAuth 连接器、审批收件箱、可回看自动化、多提供商、办公应用协作 | 优先学习“把真实工作做完”的流程；连接器和自动化必须逐项授权、逐次确认高风险动作。 |

## 2. 不可违背的架构规则

1. **Grok Build 仍是唯一 Agent 执行内核。** gorkX 不在 App 层重写 Planner、Worker 或模型循环。
2. **App 层只负责任务生命周期与可视化。** 多会话进程管理、队列、成果索引、审批和本地提醒可以由 gorkX 管；模型决策、工具调用与计划质量仍归内核。
3. **本地优先且隔离。** 运行内核只使用 App-owned `HOME` 与 `GROK_HOME`；不默默读取用户 `~/.grok`、Shell 配置或浏览器登录状态。
4. **连接器先授权再显示可用。** 普通用户走官方 OAuth/系统授权；Token、命令、配置文件只作为高级回退。没有完整链路就显示“未连接 / Soon”。
5. **高风险动作必须可见、可拒绝。** 发送消息、改日程、写远端系统、执行 Shell、外发文件，均显示目标、影响范围和确认按钮；后台任务遇到审批必须暂停，不得自行执行。
6. **结果是产品单位。** 任务完成要清楚给出可打开的文件、链接、变更、摘要与下一步，不能只留下聊天文字或猜测项目目录中的文件。
7. **无假能力。** 每项 UI 必须有真实验收、可复跑证据和失败态；不以 slash 文本、Mock、或静态卡片冒充已实现。

## 3. 能力地图

```text
用户目标
  └─ 快捷入口 / 自然语言描述                         ← gorkX
       └─ Grok Build ACP 会话与工具执行              ← gorkX 内核边界
            ├─ 同时运行的任务、状态、追加引导        ← Grok App 借鉴
            ├─ 计划、权限、外部动作的待审批收件箱    ← gorkX + OpenWorker 借鉴
            ├─ 产物、资料、变更的成果工作区          ← Grok App + OpenWorker 借鉴
            └─ OAuth 连接器与定时触发                ← OpenWorker 借鉴
```

## 4. 版本路线与验收

### P0 — 0.5.1：可信的后台多任务

**用户结果：** 可以新建第二个任务，切走后第一个任务继续运行；用户随时知道每个任务在做什么、是否需要自己决定。

| 交付 | 说明 | 验收 |
|---|---|---|
| 任务运行中心 | 侧栏显示运行/等待审批/已完成/失败四种真实状态及当前工具/计划步骤 | 两个真实 ACP 会话同时运行；切换任务不丢失流、权限或回复。 |
| 统一 Decisions 收件箱 | 跨任务聚合权限、计划审阅、结构化问题；点击只回复原任务 | 在任务 A、B 各触发一个真实请求；确认不会误发给另一任务。 |
| 运行中追加引导 | 任务运行中显示“补充说明”按钮；ACP 支持时走对应旁问/追加路由，否则明确排队为下一轮 | 已验证的内核路由才出现按钮；取消、断连、重开行为可回归。 |
| 卡顿处理 | 仅基于真实流/工具心跳显示“仍在工作 / 继续等待 / 取消” | 人为断开或超时的测试任务能准确进入可恢复错误态；不误报正常长工具调用。 |

**不做：** 不宣传“8/32 并发”这类固定数字，除非在目标机器和内核版本上压测通过。

### P1 — 0.5.2：成果与资料工作区

**用户结果：** 一次任务做出的报告、表格、图片、代码变更和资料都集中可看、可打开、可安全编辑。

| 交付 | 说明 | 验收 |
|---|---|---|
| Deliverables 面板 | 仅汇总 ACP 明确返回且本地验证过的成果，按文件/链接/变更分类 | 真实任务返回 Markdown、PDF、图片与代码文件；外部路径、符号链接、猜测出的文件均不出现。 |
| 富预览 | Markdown、图片、PDF、文本/代码优先；Office/视频分阶段接入原生或可靠预览器 | 每种已宣称类型有真实样本、打开/关闭/错误文件测试。 |
| 安全编辑 | 文本与 Markdown 的保存、冲突提示、撤销/重载；二进制只预览不伪装可编辑 | 两窗口修改同一文件时显示冲突；保存限定在选定项目。 |
| 一键交付 | 复制摘要、在 Finder 打开、导出任务记录；仅在真实成果存在时出现 | 不扫描整个项目目录；导出不泄露密钥、隐藏系统路径。 |

### P2 — 0.6：办公连接器与可控外部动作

**用户结果：** 连接 GitHub、Google/微软日历、Slack/飞书、Notion 等后，Agent 可以完成被授权的实际工作；未连接时不会假装能访问。

| 顺序 | 连接器 | 最小真实闭环 |
|---|---|---|
| 1 | GitHub | 官方浏览器授权 → 读取当前仓库 PR/Checks → 用户确认后创建 PR 或评论。 |
| 2 | 日历 | OAuth → 读取指定日程 → 提议变更 → 用户确认 → 写入 → 回执可见。 |
| 3 | Slack / 飞书 | OAuth/官方应用授权 → 读取选定频道 → 草拟回复 → 用户确认 → 发送并显示回执。 |
| 4 | Notion / Drive | OAuth → 选择页面/文件 → 读取、生成草稿或创建副本 → 用户确认写入。 |

**统一安全合同：** 每个连接器都要有“连接、权限范围、断开、重新认证、失败说明、审计记录”；不使用网页 Cookie、个人浏览器会话或剪贴板 Token 作为静默授权。

### P3 — 0.6.x：自动化与异步交付

**用户结果：** 用户可以安排“每日简报”“每周项目状态”等任务；运行过程和任何待确认动作都回到 App，绝不在后台静默外发。

| 交付 | 验收 |
|---|---|
| 自然语言创建计划任务 | 用户可查看频率、时区、数据来源、模型、权限策略与下次运行时间。 |
| 本地计划执行器 | App 关闭后使用受控 macOS Worker；每次运行都有独立任务记录、日志和成果。 |
| 审批暂停与通知 | 后台任务遇到发送/修改操作时进入 Decisions；重开 App 后仍可处理。 |
| 失败与重试 | 显示失败原因和安全的“重新运行”；不隐藏错误、不无限自动重试。 |

### P4 — 0.7：多模型的真实可用性

**用户结果：** 用户能连接并测试多家 API/兼容提供商，在任务级切换；只显示真实可用的模型和真实返回的用量。

1. 完成至少两个真实 Provider 的“配置 → 模型目录 → 连接测试 → 新任务真实回复 → 记录”闭环。
2. 给每个模型保存非敏感的最后验证时间、失败原因和适用能力（工具调用、图像等）。
3. 保留 Grok OAuth 与 App 自管内核；ChatGPT Plus / Claude Pro 网页订阅不冒充 API 授权。
4. 在每个任务详情中清楚显示实际使用的 Provider/Model，而非只显示默认值。

### P5 — 1.0：发布可信度与覆盖

| 交付 | 完成标准 |
|---|---|
| macOS 签名与公证 | 从下载到首次启动无需终端绕过；更新、回滚与崩溃诊断有明确流程。 |
| 支持 Apple Silicon 与 Intel | 两种架构分别安装、登录、跑真实项目并通过包内内核验证。 |
| Windows 试验版 | 先通过隔离数据目录、密钥存储、内核启动、真实任务与安装卸载验收。 |
| Linux 评估 | 仅在密钥存储、沙箱、桌面集成与支持成本可控后进入 Beta。 |

## 5. 优先级纪律

1. **先完成 P0，再做 P1。** 没有真实后台任务状态，成果面板和自动化会成为假工作流。
2. **连接器在 P2 才扩展。** 先把 GitHub 做成可断开、可确认、可审计的样板，再复制合同。
3. **自动化必须晚于审批收件箱。** 没有可靠暂停/恢复，不能允许后台外部动作。
4. **多模型只以真实推理验收为准。** 配置可保存或 `session/set_model` 成功，都不等于模型可用。
5. **每个阶段结束才评估发版。** 默认只推源码；没有用户明确批准，不打 tag、不发 Release、不做 DMG。

## 6. 近期执行清单

下一次开发从 P0 的以下顺序开始：

1. 审计当前 ACP Session Manager：确认是否可安全保有多个 live 会话和独立事件流。
2. 写两个会话的隔离回归：并行流、切换、权限、计划、取消、断连重连。
3. 做运行中心与 Decisions 收件箱，只消费已存在的真实事件。
4. 以一个真实 Git 项目和一个文档项目做人工验收。
5. 通过后再实现“运行中追加引导”和卡顿恢复。

## 7. 不吸收的做法

- 不把 Grok Build 换成 OpenWorker/aisuite 或另起一个 App Agent loop。
- 不为了“多模型”读取 ChatGPT/Claude 的网页订阅 Cookie。
- 不把未授权的 IM、日历、邮件、浏览器能力显示为已连接。
- 不让后台任务自动发送消息、改日程、推代码或访问全盘。
- 不以界面截图、Mock、或 slash 命令存在作为完成证据。
